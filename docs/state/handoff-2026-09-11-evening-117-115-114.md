## The finding that matters most, and it corrects an earlier claim

Measured on sim50k (N = 50,000, 210 genes, 192 FlexRV sets, 40,196 cell rows),
control `35654e19` against HEAD, paired and alternated:
**`MAC` moves on 96.4% of rows, `Pvalue_Burden` on 8.8%, median relative move
0.8% but MAX 20%.**

Earlier the same day I told the owner #118's variance-ratio consequence was
"nearly invisible on every fixture we have", from the two `null` ratios being
0.54% apart at N = 50k. That is right about the BAND and WRONG about the total,
because there are TWO routes off the per-set MAC and only one had been
separated:
  (a) which variance-ratio band is selected -- worth ~0.3%;
  (b) whether `useSparseGRM` is on at all -- a different variance ESTIMATOR.
`ctx.useSparseGRM = (MAC > m_cateVarRatioMinMACVecExclude.back())`, 20.5 at the
default, so a set whose true MAC is small now takes the sparse-GRM score test
that the CELL's MAC used to let it skip. Counted on the two output files: rows
with MAC <= 20.5 went **2,722 -> 4,287 (+57%)**.

**So #118 on real data is a statistical change to ~9% of burden p-values, not
the reporting-and-gating fix the bundled fixture makes it look like.** The
"SE moves 0.29%" figure on the row is the band alone and must not be quoted as
the size of the row. This is on LEDGER #118 and in `harness/bench/NOTES.md`.

## Cost of #118, measured and partly repaid

Peak RSS +47 to +76 MB on the 192-set arm; the `k1` and `plain` arms did not
move at all, which is the negative control that confines the growth to
`q_weight > 1`. At the largest configuration the CLI allows for FlexRV
(N = 500k, 192 sets, ONE cell -- `R/SAIGE_Test_main.R:392-400` rejects more)
that is **768 MB**. An earlier note in this session quoted 9.22 GB; that is a
12-cell figure and **12 cells cannot co-occur with 192 sets in a FlexRV run**.

User CPU was +26%, and the profile buckets split it in two:
* `emitTest` +4.0 s is the price of correctness -- the `useSparseGRM` flip above.
* `urPass` +2.4 s was overhead, now **~1.0 s repaid** (`49c1b60d`): the per-set
  `genoSumcount_noweight` accumulation replaced `arma::find` + gather + a 400 KB
  `.col()` copy with one guarded pass over a non-owning view. Output
  byte-identical (`cmp` on 40,196 rows). The remaining ~1.4 s is presumably the
  cache cost of writing 192 separate N-columns instead of one, which that change
  does not address.
  **`arma::accu` is deliberately NOT used** there: armadillo unrolls it into
  partial accumulators, a different summation order that can round differently.

Repeat the measurement with `harness/work/flexrv50k/run_twoarm.sh <lib> <tag>
<arm> <rep>` (saved from this session's scratchpad; the original `run.sh` uses
the pinned library and cannot do two arms).

## Traps this session added to the pile

* **A test that compares two different INPUTS may not assert bit-identity.**
  #117's gate is "zeroing a marker equals deleting it". On the SKAT-O path the
  deleted run's `VarMat` is one row and column smaller, so the eigen-decomposition
  differs by ~1 ULP and `expect_identical` on a p-value FAILED
  (0.406760386386861 against 0.40676038638686). The accounting columns are exact
  arithmetic over the same markers and ARE compared exactly; the statistics at
  1e-12. The BURDEN arm of the same identity IS exact, because there it is one
  sum over the same terms in the same order.
* **Do not copy `skatFailureSummary`'s `"  <n> x <msg>"` line shape.**
  `test-step2-skat-failures.R` scrapes the log with `grep("^  [0-9]+ x ")`, so a
  new summary in that shape is silently added to ITS count (8 NA cells, a tally
  summing to 10). #127's per-rule tally uses `"  rule <name>: <n> region row(s)"`.
* **`region_postprocess` is driven TWICE on the parallel SKAT-O path.** Anything
  that RECORDS rather than computes must be suppressed on the collect drive;
  `skatoCollect` passes `record_pooled = FALSE` and
  `test-unit-skato-batch.R` now asserts the sequence `(FALSE, TRUE)`.
* **A naive `make_option` sweep pairs each name with the NEXT block's default.**
  One written for #115 reported 19 mismatches, all artefacts. Parse the blocks,
  compare VALUES. The row says so; it is right.
* **`[[k]] <<- rbind(NULL, NULL)` deletes a list element.** Fixed with #126;
  see #116 below.
* **Never `git add -A` in this repo while a build may be running.** It happened
  here: a concurrent `R CMD INSTALL` had `src/CCT-58afcde1.o.tmp` on disk for a
  few seconds and `git add -A` committed it. `.gitignore` covered `src/*.o` but
  not `*.o.tmp`, so nothing stopped it. Caught only because `git status` was
  read before the push completed. Two things now guard it: `src/*.o.tmp` and
  `*.o.tmp` are ignored, and it is worth knowing that **the pre-push hook runs
  BEFORE git transfers anything**, so killing a push during its gate sends
  nothing and the commit can still be amended. `git add <paths>` is the habit to
  keep; `git ls-files | grep -E '\.o$|\.o\.tmp$|\.so$'` is the check.
